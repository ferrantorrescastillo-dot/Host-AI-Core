# 1. PROPÓSITO DE ESTE DOCUMENTO

Este documento define hacia dónde debe evolucionar Host AI, en qué orden y bajo qué condiciones.

No es una simple lista de ideas.

No es una agenda cerrada.

No es una promesa comercial.

Es el plan estratégico del proyecto.

Su función es evitar que Host AI:

- avance por impulsos;
- abra demasiadas líneas a la vez;
- priorice funciones vistosas antes que funciones necesarias;
- desarrolle capas comerciales antes de validar la operativa;
- repita trabajo ya realizado;
- mezcle objetivos de corto, medio y largo plazo;
- pierda el foco en el uso real de cocina.

Este roadmap debe responder siempre a cinco preguntas:

1. ¿Dónde estamos?
2. ¿Qué debemos terminar ahora?
3. ¿Qué depende de qué?
4. ¿Qué no debemos construir todavía?
5. ¿Qué condiciones deben cumplirse para avanzar?

---

# 2. PRINCIPIO ESTRATÉGICO CENTRAL

Host AI debe crecer desde la cocina real hacia la plataforma.

No al revés.

El orden correcto es:

```text
Uso real
↓
Validación
↓
Fiabilidad
↓
Integración
↓
Automatización
↓
IA operativa
↓
Producto comercial
↓
Escalabilidad
```

El orden incorrecto sería:

```text
Web
↓
Marketing
↓
SaaS
↓
IA llamativa
↓
Intentar adaptar después la cocina
```

Por tanto, el roadmap prioriza primero:

- piloto privado;
- flujos completos;
- consistencia de datos;
- experiencia de usuario;
- pruebas;
- trazabilidad;
- memoria del proyecto;
- consolidación técnica.

# 4. FASES MAESTRAS DEL PROYECTO

Host AI se divide en ocho grandes fases.

```text
FASE 0 — Fundamentos
FASE 1 — Piloto operativo
FASE 2 — Validación real
FASE 3 — IA operativa
FASE 4 — Automatización
FASE 5 — Producto profesional
FASE 6 — Producto comercial
FASE 7 — Plataforma escalable
```

Cada fase tiene requisitos de entrada y salida.

No debe saltarse una fase solo porque una funcionalidad posterior sea atractiva.

# 20. CRITERIOS PARA ABRIR UN SPRINT

Un sprint puede abrirse si:

- resuelve un problema real;
- pertenece a la fase activa;
- no depende de algo pendiente;
- tiene alcance claro;
- tiene datos;
- tiene motores disponibles;
- puede probarse;
- tiene criterio de cierre.

---

# 21. CRITERIOS PARA CERRAR UN SPRINT

Debe existir:

- código;
- tests;
- diagnóstico;
- regresión;
- documentación;
- evidencia;
- validación manual cuando aplique;
- actualización de memoria.

---

# 22. CRITERIOS PARA CAMBIAR DE FASE

No cambiar por calendario.

Cambiar por cumplimiento.

Ejemplo:

No pasar a producto comercial porque haya pasado un año.

Pasar cuando:

- piloto validado;
- datos fiables;
- instalación;
- soporte;
- seguridad;
- documentación.
