# HOST AI — 11.2 REGISTRO OFICIAL DE COMPONENTES

> Estándar operativo para registrar componentes reales  
> Estado: Oficial  
> Ámbito: DEVKIT / Knowledge Core  
> Versión: 1.0  
> Fecha: 13 de julio de 2026  
> Documentos relacionados: `11.1A_FILOSOFIA_Y_MODELO_DE_COMPONENTES.md`, `11.1B_FILOSOFIA_Y_MODELO_DE_COMPONENTES.md`

---

# 1. PROPÓSITO

Este documento define cómo debe registrarse cada componente real de Host AI.

Los documentos 11.1A y 11.1B establecen qué es un componente, cómo debe diseñarse y qué reglas debe respetar.

Este documento establece cómo convertir esa definición en un registro operativo, trazable y mantenible.

Su objetivo es que cualquier componente pueda responder de forma estructurada:

- qué es;
- para qué existe;
- dónde está;
- quién lo usa;
- de qué depende;
- qué datos maneja;
- qué efectos produce;
- qué pruebas lo cubren;
- qué certificaciones tiene;
- qué sprints lo modificaron;
- qué riesgos presenta;
- si está activo, obsoleto o sustituido.

---

# 2. OBJETIVO ESTRATÉGICO

El Registro Oficial de Componentes debe convertirse en la fuente estructurada para:

- inventario del proyecto;
- arquitectura viva;
- análisis de dependencias;
- mapas de impacto;
- auditorías;
- certificaciones;
- planificación de sprints;
- detección de duplicados;
- identificación de huérfanos;
- generación de documentación;
- navegación futura mediante IA.

---

# 3. PRINCIPIO FUNDAMENTAL

> Ningún componente crítico debe existir únicamente como código sin identidad registrada.

El código implementa.

El registro explica.

La certificación demuestra.

La arquitectura relaciona.

---

# 4. QUÉ SE REGISTRA

Debe registrarse cualquier componente que cumpla una o varias condiciones:

- contiene lógica de negocio;
- coordina un flujo;
- escribe datos;
- es reutilizado;
- forma parte de una entrada oficial;
- afecta stock, producción, compras, eventos o costes;
- importa datos;
- usa IA;
- tiene tests propios;
- tiene diagnóstico;
- tiene certificación;
- es crítico para un sprint.

---

# 5. QUÉ NO NECESITA REGISTRO INDEPENDIENTE

No requiere ficha propia, salvo relevancia especial:

- helper privado;
- constante local;
- función trivial;
- script temporal sin continuidad;
- fixture de test;
- archivo generado;
- documentación auxiliar;
- carpeta vacía;
- dato aislado.

Puede registrarse como parte de un componente mayor.

---

# 6. UNIDAD DE REGISTRO

La unidad oficial es el componente lógico.

Un componente puede corresponder a:

- un archivo;
- una clase;
- un paquete;
- varios archivos;
- un flujo;
- un servicio transversal;
- una capacidad operativa.

La ficha debe evitar tanto la fragmentación excesiva como la agrupación imprecisa.

---

# 7. IDENTIFICADOR OFICIAL

Formato recomendado:

```text
CMP-<DOMINIO>-<NÚMERO>
```

Ejemplos:

```text
CMP-STOCK-001
CMP-PROD-001
CMP-JORNADA-001
CMP-RCP-001
CMP-MENU-001
CMP-DEVKIT-001
```

El identificador debe ser:

- único;
- estable;
- legible;
- independiente del nombre físico del archivo;
- no reutilizable.

# 9. REGLAS DE IDENTIFICACIÓN

No debe usarse el nombre del sprint como identificador del componente.

Correcto:

```text
CMP-PROD-002
```

Incorrecto:

```text
CMP-PILOTO-1.4
```

El sprint modifica el componente.

No define su identidad permanente.

---

# 10. NOMBRE OFICIAL

El nombre debe describir el componente.

Ejemplos:

- MotorStock;
- Producción Guiada;
- ServicioProduccionStock;
- Mi Jornada;
- Importador de Menús I1.3;
- Recepción Inteligente.

Debe evitar:

- nombres genéricos;
- nombres temporales;
- numeraciones confusas;
- sufijos como final, nuevo, bueno o definitivo.

- invariantes;
- errores;
- efectos laterales;
- persistencia;
- rollback;
- certificación;
- riesgos;

---

# 18. PROPÓSITO

Debe responder:

> ¿Por qué existe este componente?

Ejemplo:

> Gestionar movimientos y disponibilidad de stock de forma trazable.

---

# 19. PROBLEMA QUE RESUELVE

Debe describirse desde la operación.

Ejemplo:

> El sistema necesita registrar entradas y salidas sin modificar existencias de forma silenciosa.

---

# 20. RESPONSABILIDAD PRINCIPAL

Debe ser única y clara.

Ejemplo:

> Aplicar y consultar movimientos de stock.

---

# 21. FUERA DE RESPONSABILIDAD

Debe indicar explícitamente qué no hace.

Ejemplo:

```text
No decide compras.
No interpreta lenguaje natural.
No muestra pantallas.
No calcula recetas.
```

---

# 22. ENTRADAS

Debe especificar:

- nombre;
- tipo;
- unidad;
- obligatoriedad;
- origen;
- validación.

Ejemplo:

```text
articulo_id: str, obligatorio
cantidad: Decimal, positiva
unidad: UnidadStock
origen: ReferenciaOperacion
```

---

# 23. SALIDAS

Debe especificar:

- tipo;
- significado;
- estado;
- errores posibles.

Ejemplo:

```text
MovimientoStock
SaldoActualizado
ResultadoOperacion
```

---

# 24. PRECONDICIONES

Ejemplos:

- artículo existente;
- unidad compatible;
- cantidad positiva;
- operación no duplicada;
- permiso suficiente.

---

# 25. POSTCONDICIONES

Ejemplos:

- movimiento registrado;
- saldo actualizado;
- trazabilidad creada;
- operación marcada como procesada.

---

# 26. INVARIANTES

Ejemplos:

- ningún movimiento sin origen;
- ninguna cantidad NaN;
- una producción no descuenta dos veces;
- un artículo conserva identificador estable.

---

# 27. ERRORES

Debe registrar:

- ID;

# 49. LIMITACIONES

Debe ser honesto.

- solo Windows;
- solo SQLite;
- sin multiusuario;
- no validado en cocina;
- no probado con grandes volúmenes.

```text
MEDIA
ALTA
CRITICA
```

- escritura;

- datos;
- seguridad;

# 53. FECHAS

- creación;

- próxima revisión;

# 58. REGLA DE FUENTE DE VERDAD

El registro estructurado será la fuente de verdad para metadatos.

El Pasaporte será la explicación humana.

El código será la implementación real.

Las tres fuentes deben reconciliarse.

```text

3. Asignar ID
4. Definir tipo y dominio

6. Definir contrato
7. Registrar archivos
8. Registrar dependencias
9. Añadir tests
10. Revisar
11. Marcar oficial
```

# 60. MODIFICACIÓN DE COMPONENTE

Debe registrar:

- motivo;
- sprint;
- cambios;
- contrato afectado;
- consumidores;
- tests;
- recertificación.

---

# 61. DEPRECACIÓN

Debe registrar:

- motivo;
- sustituto;
- fecha;
- consumidores pendientes;
- plan de migración;
- fecha límite.

---

# 62. RETIRADA

Debe comprobar:

- imports;
- llamadas dinámicas;
- configuración;
- datos;
- documentación;
- tests;
- scripts externos;
- sustituto.

---

# 63. REACTIVACIÓN

Un componente retirado puede reactivarse solo mediante:

- motivo;
- sprint;
- auditoría;
- actualización de contrato;
- pruebas;
- nueva certificación.

---

# 64. REVISIÓN PERIÓDICA

Frecuencia sugerida:

- críticos: cada sprint relevante;
- activos: trimestral;
- estables: semestral;
- deprecados: hasta retirada;
- experimentales: fecha fija.

---

# 65. CONTROL DE CAMBIOS


---

# 66. DETECCIÓN DE DESACTUALIZACIÓN

Señales:

- archivo ya no existe;
- nuevo consumidor no registrado;
- tests cambiaron;
- certificación venció;
- contrato difiere;
- estado incorrecto;
- componente sustituido.

---

# 67. RECONCILIACIÓN

Proceso:

```text
registro
vs
código
vs
tests
vs
documentación
vs
Git
```

Las diferencias deben generar pendientes.

---

# 68. AUDITORÍA AUTOMÁTICA FUTURA

Comandos:

```text
host componentes auditar
host componente revisar CMP-STOCK-001
host componentes desactualizados
host componentes sin-tests
host componentes sin-certificar
```

---

# 69. DETECCIÓN DE DUPLICADOS

Criterios:

- propósito similar;
- mismas entradas;
- mismas salidas;
- mismos datos;
- mismos consumidores;
- nombres parecidos;
- versiones paralelas.

El resultado automático será una sospecha, no una decisión final.

---

# 70. DETECCIÓN DE HUÉRFANOS

Criterios:

- sin consumidores;
- sin entrada;
- sin tests;
- sin uso;
- sin documentación;
- sin cambios recientes.

---

# 71. MAPA DE IMPACTO

Se calcula mediante:

- consumidores;
- dependencias;
- tests;
- flujos;
- certificaciones;
- sprints.

## 114.5 Intercambio externo de completado de recetas

- Componente: `SERVICIOS/recipe_completion_exchange_service.py`.
- Contrato: `HOSTAI_RECIPE_COMPLETION_PACKAGE`, versión de exportación `0.3` compatible en importación con `0.1` y `0.2`, libro XLSX con hojas `METADATA`, `INSTRUCCIONES`, `SCHEMA` y `RECETAS`.
- Responsabilidad: exportar contexto canónico y validar propuestas reimportadas; no tiene autoridad de escritura.
- Frontera: una selección explícita conserva orden, elimina duplicados y nunca incorpora recetas ajenas; la selección vacía produce un paquete vacío válido.
- Integridad: cada fila conserva `recipe_id` canónico y fingerprint de los datos actuales; una receta modificada desde la exportación se rechaza como obsoleta antes del preview.
- Seguridad: límites de tamaño/filas/ZIP, schema y versión obligatorios, tipos acotados, fórmulas rechazadas, IDs inexistentes/duplicados/fuera de selección aislados y columnas de propuesta desconocidas ignoradas con trazabilidad.
- Compatibilidad física: lectura acotada independiente de `max_row/max_column`, porque editores externos válidos pueden eliminar la dimensión calculada de la hoja.
- Convergencia: las propuestas externas pasan por `RecetaDocumentacionWriteService.proposal`, la política compartida de campos, `RecetaDocumentacionBatchService`, autorización, preview, confirmación idempotente y lectura posterior existentes.
- Contrato selección/preview: `seleccion` persiste una selección filtrada e invalida cualquier preview anterior; el consumidor debe solicitar después `preview`. Solo `confirmar`, con fingerprint vigente, tiene autoridad de escritura.
- Semántica de reemplazo: las acciones seguras global y por receta reemplazan toda la selección y envían `individual_selections={}`; omitir ese miembro significa conservar las selecciones individuales existentes. Una selección crítica solo se acumula mediante la acción individual explícita.
- Detalle de preview: cada cambio expone receta, campo, valor actual/propuesto, procedencia, clasificación masiva/individual y si completa o sobrescribe; los campos no seleccionados no forman parte del fingerprint ni de la confirmación.
- Semántica de validación: utilidad segura y revisión crítica son dimensiones no excluyentes; una misma fila puede alimentar selección masiva y conservar campos individuales/bloqueados para revisión.
- Procedencia: `fuente_propuesta=ARCHIVO_EXTERNO` y `origen_externo` cerrado a `CHATGPT`, `OPENAI_API`, `OTRO_PROVEEDOR_IA`, `HUMANO` o `ARCHIVO_EXTERNO`; una reimportación nunca se convierte en dato `REAL` por sí sola.
- Consumidor UI: Biblioteca → Importaciones → `Completar externamente con XLSX`; muestra recibo por nombre/SHA-256, conteos simultáneos, alerta ante plantilla sin propuestas y ejecuta selección → preview como dos operaciones explícitas sin escritura.
- Continuidad UI: el resumen conserva el identificador del batch externo por importación, lo rehidrata mediante el GET canónico y ofrece un CTA contextual para volver a propuestas sin reimportar ni crear otra autoridad; preview permite regresar a propuestas.
- Persistencia de workflow: la API de producto activa persistencia de sesiones normalizadas en `biblioteca_importaciones_web.json`; `RecipeCompletionBatchRepository` conserva batch externo, propuestas, selecciones, preview y confirmaciones idempotentes en `biblioteca_completado_recetas_batches.json`. Ambos usan escritura segura y no alteran recetas antes de confirmar.
- Reconstrucción: el detalle canónico de importación incluye `completado_recetas_activo`; React reconstruye desde esa respuesta tras remount/F5/reapertura. El almacenamiento del navegador sólo aporta el identificador de la sesión y no es autoridad de propuestas o selección.
- Descubrimiento sin puntero local: `GET /api/v1/biblioteca/importaciones` enumera las sesiones activas por `updated_at`; la UI consulta el listado cuando no existe pista en `sessionStorage/localStorage` y recupera el detalle canónico. El listado publica una ruta de storage relativa, nunca la ruta absoluta del servidor.
- Ciclo de vida: sesión y batch son durables; la vista es reconstruible; el XLSX binario es temporal y no se retiene después de normalizar y validar sus propuestas.
- Recuperación post-confirmación: el último batch externo durable continúa enlazado y revisable cuando está `COMPLETADO` o `COMPLETADO_PARCIAL`; solo un batch `CANCELADO` deja de publicarse como recuperable. La revisión no repite la escritura.
- Diagnóstico: `SCRIPTS/COMPROBAR_FASE1_COMPLETADO_EXTERNO.py`, siempre sobre copia temporal y sin confirmación.
- Tests: `TESTS/test_recipe_completion_exchange.py`, regresión de batch/workflow, `HOST_AI_WEB/src/__tests__/biblioteca-importaciones.test.tsx` y E2E real `HOST_AI_WEB/e2e/biblioteca-import-persistence.spec.ts` con servidor aislado `TESTS/fase1_e2e_server.py`.
- Estado: implementado y probado técnicamente el 1 de septiembre de 2026; validación humana final pendiente.

### Ampliación operativa 0.2
