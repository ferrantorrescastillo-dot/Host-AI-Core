# 1. PROPÓSITO

Este documento define la filosofía y el modelo oficial de componentes de Host AI.

Su función es establecer un lenguaje común para describir, diseñar, revisar y evolucionar cualquier pieza del sistema.

A partir de este documento, toda parte relevante de Host AI deberá poder responder:

- qué responsabilidad tiene;
- qué problema resuelve;
- qué entradas acepta;
- qué salidas produce;
- de qué depende;
- quién depende de ella;
- qué no debe hacer;
- cómo se prueba;
- cómo se certifica;
- cómo se sustituye;
- cómo se retira.

Este documento no inventa la arquitectura real del proyecto.

Define las reglas conceptuales con las que deberá auditarse y describirse esa arquitectura.

---

# 2. IDEA CENTRAL

Host AI debe construirse como un sistema de componentes con responsabilidades claras.

Un componente no es simplemente un archivo.

Un archivo puede contener varios elementos.

Un componente es una unidad lógica con propósito propio.

La regla principal es:

> Cada componente debe existir porque resuelve una responsabilidad concreta del sistema.

Si no puede explicarse con claridad qué responsabilidad tiene, el componente está mal definido.

---

# 3. POR QUÉ HOST AI NECESITA UN MODELO DE COMPONENTES

Host AI ha crecido hasta convertirse en un proyecto amplio.

Dispone de:

- motores;
- servicios;
- consolas;
- importadores;
- modelos;
- datos;
- pruebas;
- diagnósticos;
- documentación;
- componentes históricos;
- parches;
- sprints;
- versiones.

Sin un modelo común, aparecen riesgos:

- duplicar lógica;
- crear servicios que hacen lo mismo;
- mezclar presentación y negocio;
- romper contratos;
- mantener archivos obsoletos;
- no saber qué depende de qué;
- no poder certificar con precisión;
- no saber si un componente puede retirarse;
- crear arquitectura teórica distinta al código real.

El modelo de componentes reduce estos riesgos.

---

# 4. DEFINICIÓN OFICIAL DE COMPONENTE

Un componente de Host AI es:

> Una unidad lógica identificable, con una responsabilidad principal, un contrato definido y relaciones explícitas con otras partes del sistema.

Un componente puede estar implementado mediante:

- un archivo;
- varios archivos;
- una clase;
- un conjunto de funciones;
- un paquete;
- un servicio;
- un motor;
- una interfaz;
- un adaptador;
- una configuración;
- una estructura de datos.

La implementación física no define por sí sola el componente.

Lo define su responsabilidad.

---

# 5. CARACTERÍSTICAS DE UN COMPONENTE

Un componente bien definido debe tener:

- nombre;
- propósito;
- responsabilidad principal;
- entradas;
- salidas;
- dependencias;
- consumidores;
- errores posibles;
- reglas;
- pruebas;
- estado;
- versión;
- documentación;
- propietario lógico.

No todos estos datos deben aparecer en el código.

Pero deben poder conocerse.

---

# 6. QUÉ NO ES UN COMPONENTE

No es necesariamente:

- cada archivo Python;
- cada función;
- cada carpeta;
- cada clase;
- cada sprint;
- cada pantalla;
- cada tabla;
- cada script temporal.

Un archivo solo se considera componente si representa una responsabilidad lógica estable.

---

# 7. COMPONENTE VS ARCHIVO

Un componente puede abarcar varios archivos.

Ejemplo:

```text
Producción guiada
├── servicio
├── consola
├── tests
├── diagnóstico
└── certificación
```

El componente lógico es “Producción guiada”.

Los archivos son sus implementaciones y evidencias.

---

# 8. COMPONENTE VS MÓDULO

Un módulo es una unidad física de código.

Un componente es una unidad lógica.

Un módulo puede implementar un componente.

Varios módulos pueden colaborar para implementarlo.

Un mismo módulo no debería implementar componentes sin relación clara.

---

# 9. COMPONENTE VS SERVICIO

Un servicio es un tipo de componente.

Su función principal es coordinar.

No todos los componentes son servicios.

Un motor, un modelo o una interfaz también son componentes.

---

# 10. COMPONENTE VS MOTOR

Un motor es un componente que contiene lógica determinista de negocio.

Ejemplos:

- calcular stock;
- escalar una receta;
- priorizar tareas;
- generar un pedido;
- validar disponibilidad.

El motor debe poder funcionar sin interfaz.

---

# 11. COMPONENTE VS FLUJO

Un flujo es una secuencia de componentes.

Ejemplo:

```text
He terminado una producción
↓
Consola
↓
Servicio coordinador
↓
Motor de producción
↓
Motor de stock
↓
Persistencia
↓
Mi Jornada
```

El flujo no sustituye a los componentes.

Los conecta.

---

# 12. COMPONENTE VS SPRINT

Un sprint modifica o crea componentes.

El sprint no es parte de la arquitectura operativa.

Es una unidad de evolución.

Un componente puede haber sido modificado por varios sprints.

---

# 13. PRINCIPIO DE RESPONSABILIDAD ÚNICA

Cada componente debe tener una responsabilidad principal.

Esto no significa que solo pueda contener una función.

Significa que todas sus funciones deben contribuir al mismo propósito.

Ejemplo correcto:

> Servicio que coordina el cierre de una producción y sus movimientos de stock.

Ejemplo incorrecto:

> Servicio que cierra producción, genera informes, envía correos, calcula costes y modifica recetas.

---

# 14. PREGUNTA DE RESPONSABILIDAD

Para validar un componente debe poder completarse:

> Este componente existe para __________.

Si la respuesta contiene varias responsabilidades independientes, debe revisarse.

---

# 15. RESPONSABILIDAD PRINCIPAL Y SECUNDARIAS

Un componente puede tener responsabilidades secundarias si apoyan la principal.

Ejemplo:

Responsabilidad principal:

> Coordinar producción y stock.

Secundarias:

- validar precondiciones;
- construir vista previa;
- registrar trazabilidad;
- gestionar rollback.

Todas pertenecen al mismo objetivo.

---

# 16. PRINCIPIO DE COHESIÓN

La cohesión mide cuánto pertenecen entre sí las partes de un componente.

Alta cohesión:

- todas las funciones trabajan sobre el mismo problema;
- comparten modelo;
- comparten reglas;
- cambian por razones similares.

Baja cohesión:

- mezcla tareas sin relación;
- cambia por muchas razones;
- contiene utilidades aleatorias;
- depende de muchas áreas.

Host AI debe preferir componentes de alta cohesión.

---

# 17. INDICADORES DE ALTA COHESIÓN

- propósito fácil de explicar;
- nombre preciso;
- pocas razones de cambio;
- pruebas concentradas;
- dependencias relacionadas;
- datos comunes;
- interfaz estable.

---

# 18. INDICADORES DE BAJA COHESIÓN

- nombre genérico;
- demasiadas funciones no relacionadas;
- mezcla de dominios;
- constantes de muchas áreas;
- imports dispersos;
- cambios frecuentes por motivos distintos;
- dificultad para probar.

---

# 19. PRINCIPIO DE ACOPLAMIENTO BAJO

El acoplamiento mide cuánto depende un componente de otros.

Host AI debe reducir dependencias innecesarias.

Bajo acoplamiento no significa cero dependencias.

Significa dependencias:

- necesarias;
- explícitas;
- estables;
- limitadas;
- sustituibles.

---

# 20. ACOPLAMIENTO ACEPTABLE

Es aceptable cuando:

- el componente necesita realmente la dependencia;
- el contrato es claro;
- la dependencia tiene responsabilidad estable;
- puede simularse en tests;
- no obliga a conocer detalles internos.

---

# 21. ACOPLAMIENTO PELIGROSO

Ocurre cuando:

- un componente accede a datos internos de otro;
- importa demasiadas capas;
- depende de rutas físicas;
- modifica estructuras ajenas;
- llama funciones no públicas;
- necesita conocer detalles de implementación.

---

# 22. ACOPLAMIENTO CIRCULAR

Existe cuando:

```text
A depende de B
B depende de A
```

Debe evitarse.

Soluciones:

- extraer contrato común;
- introducir servicio coordinador;
- separar modelo compartido;
- invertir dependencia;
- eliminar responsabilidad duplicada.

---

# 23. PRINCIPIO DE ENCAPSULACIÓN

Cada componente debe ocultar sus detalles internos.

Los consumidores deben conocer:

- qué pueden pedir;
- qué reciben;
- qué errores pueden ocurrir.

No deberían conocer:

- cómo calcula;
- cómo persiste;
- qué funciones internas usa;
- qué variables internas modifica.

---

# 24. INTERFAZ PÚBLICA

Todo componente relevante debe tener una interfaz pública reconocible.

Puede ser:

- métodos;
- funciones;
- eventos;
- comandos;
- modelos;
- endpoints futuros.

La interfaz pública debe ser más estable que la implementación interna.

---

# 25. DETALLES INTERNOS

Deben considerarse internos:

- helpers;
- normalizadores;
- validadores locales;
- cachés;
- estructuras temporales;
- funciones auxiliares;
- implementación de persistencia.

No deben consumirse desde otros componentes salvo contrato explícito.

---

# 26. PRINCIPIO DE COMPOSICIÓN

Host AI debe preferir construir flujos combinando componentes existentes.

Ejemplo:

```text
Producción → Stock
```

debe combinar:

- motor de producción;
- motor de stock;
- servicio de trazabilidad;
- interfaz guiada.

No debe crear un segundo motor que repita todo.

---

# 27. COMPOSICIÓN VS DUPLICACIÓN

Composición:

- reutiliza;
- coordina;
- conserva autoridad;
- reduce divergencia.

Duplicación:

- copia reglas;
- crea resultados distintos;
- aumenta mantenimiento;
- dificulta certificación.

Regla:

> Antes de crear lógica nueva, buscar el componente que ya posee esa responsabilidad.

---

# 28. PRINCIPIO DE CONTRATO

Los componentes se relacionan mediante contratos.

Un contrato define:

- entrada;
- salida;
- errores;
- efectos;
- precondiciones;
- garantías;
- compatibilidad.

Un contrato no necesita ser formal al principio.

Pero debe ser explícito.

---

# 29. PRECONDICIONES

Condiciones que deben cumplirse antes de ejecutar.

Ejemplo:

Para cerrar producción:

- tarea válida;
- receta disponible;
- cantidad conocida;
- stock suficiente;
- operación no registrada.

---

# 30. POSTCONDICIONES

Garantías después de ejecutar correctamente.

Ejemplo:

- materias primas descontadas;
- producto terminado añadido;
- tarea cerrada;
- trazabilidad registrada;
- operación marcada como procesada.

---

# 31. INVARIANTES

Reglas que siempre deben mantenerse.

Ejemplos:

- una producción no descuenta stock dos veces;
- un movimiento debe tener origen;
- una certificación debe tener versión;
- un `A.P` no se degrada automáticamente a materia prima.

---

# 32. ERRORES DEL CONTRATO

Un contrato debe definir errores esperados.

Ejemplos:

- stock insuficiente;
- receta no encontrada;
- unidad incompatible;
- duplicado;
- permiso insuficiente;
- datos incompletos.

---

# 33. EFECTOS LATERALES

Un componente debe declarar si:

- escribe datos;
- modifica estado;
- crea archivos;
- genera movimientos;
- envía mensajes;
- cambia configuración.

Los efectos laterales ocultos son peligrosos.

---

# 34. COMPONENTES PUROS

Un componente puro:

- recibe datos;
- calcula;
- devuelve resultado;
- no modifica nada externo.

Son preferibles para:

- cálculos;
- validaciones;
- normalizaciones;
- clasificación;
- formateo.

---

# 35. COMPONENTES CON ESTADO

Algunos componentes necesitan estado.

Ejemplos:

- repositorios;
- sesiones;
- motores persistentes;
- colas;
- bandeja.

El estado debe ser:

- explícito;
- controlado;
- trazable;
- recuperable.

---

# 36. COMPONENTES DE COORDINACIÓN

Un servicio coordinador puede:

- llamar motores;
- validar secuencia;
- preparar vista previa;
- ejecutar transacción;
- traducir errores;
- devolver resultado.

No debe duplicar la lógica interna de los motores.

---

# 37. COMPONENTES DE PRESENTACIÓN

La interfaz puede:

- mostrar;
- preguntar;
- recoger intención;
- confirmar;
- formatear;
- navegar.

No debe:

- calcular stock;
- decidir escandallos;
- modificar datos directamente;
- contener reglas complejas.

---

# 38. COMPONENTES DE PERSISTENCIA

Deben responsabilizarse de:

- guardar;
- leer;
- consultar;
- versionar;
- migrar;
- bloquear;
- transaccionar.

No deben decidir prioridades culinarias.

---

# 39. COMPONENTES DE DOMINIO

Representan conceptos reales:

- artículo;
- receta;
- evento;
- producción;
- tarea;
- recepción;
- movimiento;
- bloqueo.

Deben usar lenguaje del negocio.

---

# 40. PRINCIPIO DE DEPENDENCIA HACIA EL DOMINIO

La lógica de dominio no debería depender de la interfaz.

Ejemplo correcto:

```text
Consola → Servicio → Motor
```

Ejemplo incorrecto:

```text
Motor → Consola
```

---

# 41. DIRECCIÓN DE DEPENDENCIAS

Dirección preferida:

```text
APP
↓
SERVICIOS
↓
CORE / DOMINIO
↓
PERSISTENCIA MEDIANTE CONTRATO
```

Los detalles pueden variar según el código real.

La regla conceptual es que las capas externas dependan del núcleo, no al revés.

---

# 42. INVERSIÓN DE DEPENDENCIAS

Cuando un motor necesita persistencia, debe depender de una interfaz o contrato, no de detalles innecesarios.

Ejemplo conceptual:

```text
MotorStock
↓
RepositorioStock
```

No:

```text
MotorStock
↓
Ruta concreta de SQLite
```

---

# 43. PRINCIPIO DE SUSTITUCIÓN

Un componente compatible debe poder sustituirse sin romper a sus consumidores.

Ejemplo:

Un repositorio de prueba debe poder sustituir al repositorio real si cumple el mismo contrato.

---

# 44. PRINCIPIO DE INTERFACES PEQUEÑAS

Los consumidores no deberían depender de operaciones que no necesitan.

Mejor:

```text
consultar_stock()
registrar_entrada()
registrar_salida()
```

que una interfaz enorme e indiscriminada.

---

# 45. PRINCIPIO DE ESTABILIDAD

Los componentes muy utilizados deben tener contratos estables.

Los cambios incompatibles deben:

- versionarse;
- migrarse;
- documentarse;
- probarse;
- recertificarse.

---

# 46. PRINCIPIO DE EXPLICITUD

Host AI debe preferir:

- dependencias explícitas;
- estados explícitos;
- errores explícitos;
- unidades explícitas;
- versiones explícitas.

Debe evitar:

- comportamiento mágico;
- inferencias ocultas;
- escritura silenciosa;
- defaults peligrosos.

---

# 47. PRINCIPIO DE TRAZABILIDAD

Todo componente con impacto operativo debe permitir saber:

- quién lo llamó;
- qué recibió;
- qué decidió;
- qué escribió;
- qué resultado produjo;
- qué error ocurrió.

---

# 48. PRINCIPIO DE IDEMPOTENCIA

Las operaciones que no deben duplicarse deben ser idempotentes.

Ejemplo:

Registrar la misma producción dos veces no debe descontar dos veces.

---

# 49. PRINCIPIO DE TRANSACCIÓN

Si varios cambios forman una única operación, deben tratarse como unidad.

Ejemplo:

```text
descontar ingredientes
+ añadir elaboración
+ cerrar tarea
+ registrar trazabilidad
```

Si falla una parte crítica, debe evitarse un estado parcial.

---

# 50. PRINCIPIO DE RECUPERACIÓN

Un componente que escribe debe definir:

- rollback;
- compensación;
- reintento;
- estado de error;
- recuperación manual.

---

# 51. PRINCIPIO DE OBSERVABILIDAD

Debe ser posible diagnosticar:

- entradas;
- salidas;
- tiempos;
- errores;
- estado;
- dependencias.

Sin observabilidad, un componente no puede certificarse bien.

---

# 52. PRINCIPIO DE PRUEBAS AISLADAS

Un componente debe poder probarse sin usar datos reales.

Debe permitir:

- fixtures;
- repositorios temporales;
- mocks cuando proceda;
- rutas aisladas;
- resultados reproducibles.

---

# 53. PRINCIPIO DE CONFIGURACIÓN EXTERNA

Los valores variables no deben incrustarse sin necesidad.

Ejemplos:

- rutas;
- hojas;
- unidades;
- límites;
- estados;
- permisos;
- formatos.

---

# 54. PRINCIPIO DE COMPATIBILIDAD

Antes de cambiar un contrato debe comprobarse:

- quién lo usa;
- qué tests lo cubren;
- qué sprints dependen;
- qué certificaciones afecta;
- qué migración requiere.

---

# 55. PRINCIPIO DE MÍNIMA SORPRESA

Un componente debe comportarse como su nombre y contrato hacen esperar.

Una función llamada:

```text
consultar_stock()
```

no debe modificar stock.

---

# 56. PRINCIPIO DE FALLO SEGURO

Ante error, el componente debe preferir:

- no escribir;
- bloquear;
- devolver diagnóstico;
- conservar datos;
- pedir confirmación.

---

# 57. PRINCIPIO DE INFORMACIÓN SUFICIENTE

Los errores deben incluir contexto útil sin exponer detalles innecesarios.

Ejemplo:

> No puede cerrarse la producción porque faltan 4,70 kg de carrillera.

No:

> KeyError línea 247.

---

# 58. PRINCIPIO DE FRONTERA CLARA

Cada componente debe tener frontera.

Dentro:

- reglas propias;
- estado propio;
- implementación.

Fuera:

- contrato;
- eventos;
- resultados;
- errores.

---

# 59. PRINCIPIO DE PROPIEDAD DE DATOS

Debe quedar claro qué componente es autoridad sobre cada dato.

Ejemplos:

- MotorStock: movimientos y existencias;
- MotorProduccionReal: estado de tareas;
- Recetas: definición culinaria;
- Mi Jornada: agregación, no fuente original.

---

# 60. FUENTE DE VERDAD

No deben existir dos componentes activos con autoridad sobre el mismo concepto sin regla de sincronización.

---

# 61. COMPONENTES AGREGADORES

Un agregador reúne información de varias fuentes.

Ejemplo:

`Mi Jornada`.

No debe convertirse automáticamente en autoridad sobre los datos originales.

---

# 62. COMPONENTES ADAPTADORES

Un adaptador traduce entre formatos o contratos.

Ejemplos:

- Excel a modelo interno;
- proveedor a artículo;
- consola a comando;
- IA a intención estructurada.

No debe inventar lógica de negocio.

---

# 63. COMPONENTES ORQUESTADORES

Un orquestador decide el orden de llamadas.

No debe recalcular lo que ya calculan los motores.

---

# 64. COMPONENTES DE POLÍTICA

Contienen reglas configurables.

Ejemplos:

- prioridad;
- selección de lote;
- proveedor preferido;
- calendario.

Deben distinguirse de datos y mecanismos.

---

# 65. COMPONENTES DE MECANISMO

Ejecutan operaciones.

Ejemplos:

- persistir;
- mover stock;
- leer archivo;
- crear backup.

No deben decidir estrategia de negocio.

---

# 66. COMPONENTES COMPARTIDOS

Solo deben ser compartidos si:

- tienen propósito claro;
- son estables;
- no acumulan utilidades sin relación;
- no crean dependencias circulares.

---

# 67. CARPETA DE UTILIDADES

Una carpeta `utils` puede convertirse en vertedero.

Toda utilidad debe:

- tener dominio o propósito;
- estar probada;
- tener nombre claro;
- no esconder reglas de negocio.

---

# 68. COMPONENTES TEMPORALES

Un script temporal debe indicar:

- motivo;
- alcance;
- fecha;
- caducidad;
- criterio de retirada.

No debe convertirse silenciosamente en dependencia permanente.

---

# 69. COMPONENTES LEGADO

Un componente legado puede mantenerse si:

- sigue siendo necesario;
- no puede migrarse aún;
- su riesgo está controlado;
- está documentado;
- tiene plan de sustitución.

---

# 70. COMPONENTES OBSOLETOS

Debe marcarse obsoleto cuando:

- existe sustituto;
- no tiene consumidores;
- su contrato ya no es vigente;
- solo se conserva por historia.

No debe eliminarse sin verificar dependencias.

---

# 71. COMPONENTES HUÉRFANOS

Un componente huérfano:

- no tiene consumidores conocidos;
- no tiene entrada;
- no tiene tests;
- no aparece en flujos.

Debe auditarse antes de eliminar.

---

# 72. COMPONENTES DUPLICADOS

Se sospecha duplicación si:

- nombres diferentes calculan lo mismo;
- varios servicios escriben el mismo dato;
- existen versiones numeradas activas;
- tests cubren comportamientos equivalentes.

---

# 73. COMPONENTES CRÍTICOS

Son críticos si:

- escriben datos;
- calculan costes;
- modifican stock;
- gestionan producción;
- importan documentos;
- controlan permisos;
- coordinan transacciones.

Requieren más pruebas y certificación.

---

# 74. COMPONENTES DE ALTO USO

Un componente muy utilizado debe priorizar:

- estabilidad;
- compatibilidad;
- observabilidad;
- documentación;
- rendimiento.

---

# 75. COMPONENTES EXPERIMENTALES

Deben estar:

- aislados;
- marcados;
- fuera de producción;
- sin datos reales;
- con fecha de revisión.

---

# 76. REGLA DE CREACIÓN

Antes de crear un componente:

1. definir problema;
2. buscar equivalente;
3. revisar arquitectura;
4. revisar contratos;
5. definir responsabilidad;
6. definir consumidores;
7. definir pruebas;
8. justificar archivo nuevo.

---

# 77. REGLA DE MODIFICACIÓN

Antes de modificar:

1. localizar consumidores;
2. revisar tests;
3. revisar certificaciones;
4. revisar contratos;
5. evaluar compatibilidad;
6. crear regresión.

---

# 78. REGLA DE RETIRADA

Antes de retirar:

1. buscar imports;
2. buscar llamadas dinámicas;
3. revisar entradas;
4. revisar documentación;
5. revisar datos;
6. ofrecer sustituto;
7. conservar historial.

---

# 79. REGLA DE NOMBRES

El nombre debe reflejar responsabilidad.

Buenos ejemplos:

- `MotorStock`
- `ServicioProduccionStock`
- `RepositorioArticulos`
- `ConsolaProduccionGuiada`

Malos ejemplos:

- `gestor_general`
- `utils2`
- `nuevo_final`
- `motor_total`

---

# 80. REGLA DE TAMAÑO

No existe tamaño universal.

Debe dividirse si:

- tiene varias razones de cambio;
- es difícil de probar;
- mezcla dominios;
- tiene demasiadas dependencias;
- su interfaz es confusa.

---

# 81. REGLA DE SIMPLICIDAD

La arquitectura debe ser tan simple como permita el problema real.

No crear capas solo por parecer profesional.

Cada capa debe aportar:

- separación;
- seguridad;
- reutilización;
- claridad;
- testabilidad.

---

# 82. REGLA DE EVOLUCIÓN

Un componente puede empezar simple y evolucionar.

Debe evitarse diseñar desde el principio para escenarios hipotéticos lejanos.

---

# 83. REGLA DE DOMINIO

El nombre y contrato deben usar conceptos del negocio.

Preferir:

- recepción;
- producción;
- artículo;
- receta;
- evento;
- bloqueo.

Evitar nombres abstractos que oculten el proceso real.

---

# 84. REGLA DE INTERFAZ HUMANA

Los componentes internos pueden usar estructuras técnicas.

La interfaz final debe traducirlas a lenguaje de cocina.

---

# 85. REGLA DE IA

La IA debe consumir contratos.

No debe acceder libremente a cualquier dato ni escribir directamente sin validación.

---

# 86. REGLA DE CERTIFICACIÓN

Cada componente crítico debe poder vincularse a:

- tests;
- diagnóstico;
- pasaporte;
- certificación;
- versión.

---

# 87. REGLA DE SPRINTS

Todo sprint debe indicar qué componentes:

- crea;
- modifica;
- sustituye;
- retira;
- recertifica.

---

# 88. REGLA DE ROADMAP

Un componente nuevo debe pertenecer a una fase o justificar su carácter transversal.

---

# 89. REGLA DE BACKLOG

Una sospecha de duplicidad, huérfano o deuda debe registrarse en `10_PENDIENTES.md`.

---

# 90. REGLA DE MEMORIA

Las decisiones permanentes deben registrarse en la memoria técnica.

# 95. INDICADORES DE BUEN COMPONENTE

- responsabilidad clara;
- nombre preciso;
- pocas dependencias;
- contrato estable;
- pruebas aisladas;
- errores comprensibles;
- sin efectos ocultos;
- trazabilidad;
- documentación;
- consumidores conocidos.

---

# 96. INDICADORES DE COMPONENTE PROBLEMÁTICO

- demasiados imports;
- nombre genérico;
- varias responsabilidades;
- datos globales;
- escritura directa;
- lógica de interfaz;
- sin tests;
- sin consumidores conocidos;
- contratos implícitos;
- duplicidad.

# 100. DECISIONES OFICIALES DE ESTA PARTE

1. Host AI se describirá mediante componentes lógicos.
2. Archivo y componente no son equivalentes.
3. Cada componente tendrá responsabilidad principal.
4. Se priorizará alta cohesión y bajo acoplamiento.
5. Las relaciones se harán mediante contratos.
6. La interfaz no contendrá lógica crítica.
7. Los servicios coordinarán sin duplicar motores.
8. Los efectos laterales serán explícitos.
9. Los componentes críticos serán trazables y certificables.
10. La arquitectura real se auditará usando este modelo.
